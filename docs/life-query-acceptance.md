# Focused life queries

The client now bootstraps compact workspace context and exposes the server's small set of primary domain reads. Whole-word, intent-aware discovery supplies other read/write schemas on demand. Up to two relevant source reads and two relevant edits can be exposed directly for the current question, avoiding unnecessary generic-call envelopes while using the same validation. Large results retain bounded previews and scoped report handles. The default local model, context window and output budget are unchanged.

One `read_result` operation accepts temporary result handles and saved report handles, including a report embedded in an oversized result. Report row requests are routed to the scoped server snapshot instead of mistakenly reading only the preview. Replacement metadata excludes superseded query tools from chat discovery. Unknown operation names return authorized suggestions without executing anything. A new report or successful write invalidates a previously prepared final answer.

Financial, project, forecast, timeline, calendar and source-excerpt answers use the server's verified report renderer. The client buffers a free-form final draft after a report is retrieved and requires `present_report` instead. The exact server text ends the response without another inference step; inspection records zero inference usage for this rendering. Successful mutations invalidate a previously prepared answer. The adapter also rejects pre-write saved reports for final presentation in the same turn; reopening an old snapshot does not refresh it. Confirmations may use the returned changed-record facts, or a new query. Successful calendar writes return fresh verified receipts so even the weekday is computed by the service. A report-storage failure after commitment preserves a verified success receipt instead of inviting a duplicate create. Missing household/timezone defaults return a typed clarification before timeline retrieval; an explicit follow-up can supply them without changing settings. Ambiguous appointment times return typed choices before any mutation; the adapter displays that clarification directly. If the model ignores the forced presentation retry, the client renders the saved reports directly (up to four) instead of failing or releasing unverified prose. Complete empty calendar reports do not block qualitative explanations; financial empty-result semantics still use the renderer. The presentation tool result retains scoped report handles rather than duplicating the entire verified answer in model history; the complete assistant answer and audited MCP response remain intact. A constrained `insufficient_evidence` conclusion lets the model state that retrieved material does not establish the requested fact while preserving the verified evidence. It prevents a related report from being substituted for an answer and does not permit arbitrary model-written conclusions. Source searches allow a focused synonymous follow-up, then this limited answer; they do not need to exhaust a long note to prove absence. Qualitative questions without a saved report still use model prose. Relationship results include other verified participants in the same arrangement and support role/name filters; a list of vehicles uses typed identity search.

Before dispatching `records.recordExpense`, the client verifies the selected ledger-account identities and requires payment-account and expense-category references in retained original user messages. Category references accept a named category or recognizable category terms; unknown merchant/category mappings require clarification. Model-generated summaries, source notes and earlier database transactions cannot supply this reference. This is a necessary check against guessing an unspecified payment account, not a complete semantic authorization proof. If the original user reference has fallen out of retained history, the user must restate it. Explicit credit-card charges use the server’s designated card liability and do not reduce bank cash.

The same original-user account check applies to hypothetical one-off cash movements. Discovering an available account does not authorize choosing it, even for a simulation. A missing choice produces a direct question and prevents later operations in that batch; a retained follow-up choice can complete the scenario. Recurring changes use the already recorded cash route instead. An unresolved account name or suffix passed as a database ID returns a recoverable reference error: resolve the account already named by the user and retry. It does not falsely turn an explicit user choice into a missing-choice clarification.

Current unpaid invoices use `life.obligations` with required receivable/payable/both direction, explicit scope and optional debtor/creditor filters. Household scope supplies our perspective; a uniquely named `perspectiveQuery` supports another person/company, separately from a counterparty filter. They are separate from loan principal, future scheduled cash, and unincurred project assumptions. Related planned work appears separately when relevant. Timeline results must be complete before presentation. Relationship results disclose their exact filters so a filtered ownership lookup cannot support a global claim about every owner.

Document reads accept returned document IDs directly and return the owning target. Focused queries search a known document for any of the requested normalized words, returning bounded exact excerpts or a scoped absence. Missing documents are not complete searches. An age alone cannot establish a birthday; bank balances alone cannot establish market net worth.

Calendar creates and corrections accept an absolute date or a bounded relative `dateExpression`. The client retains simple relative phrases from the current original user request before argument validation and idempotency-key generation; the service resolves them using the selected timezone or the existing event. This prevents a model-guessed absolute date from replacing “next Tuesday” or “two days later.” `time=same` preserves the recorded local clock time. Mixed origin/destination, negated and explicit-date clauses are not automatically rewritten. Named participants must be explicitly linked, and new events use canonical calendar categories.

The server implementation and independent arithmetic fixtures live in the sibling LifeOR2 repository under `docs/decisions/life-query-contract.md` and `scripts/evaluation/`. `apps/web/scripts/eval-life-queries.ts` exercises the actual adapter, MCP transport and configured local model against the isolated local endpoint. It records tool operations, latency, token observations, errors and answers in ignored `.eval-results/` files. No private transcripts or connection credentials belong in Git.

Actual local inference and record-level acceptance completed on September 18, 2026 with the unchanged Qwen model and 32K context. Two separate fixtures each contain 308,000 journals across sixteen historical years. The final frozen 65-turn regression accepted 63 answers: one report lacked an explicit completion-guarantee limitation, and one correct receipt lookup repeated searches until almost exhausting its budget. Both failures remain in the evidence; server `f17e59a` corrected them, and six targeted actual-model follow-ups passed. Four relative-calendar turns and three unconfigured-scope turns also passed, alongside independent create/edit and bank/card reversal oracles. The scope-negative appointment attempted a call that was rejected before mutation; its conservative smoke flag remains preserved.

The original upcoming-month question passed on 308,004 journals in 29.8 seconds with one timeline query and 11,133 peak input tokens. The final core median was 74.5 seconds, with no compactions. The corrected receipt question used one journal lookup in 59.9 seconds; prior redundant-search latency remains documented. These are observed shared-host timings, not a controlled speedup claim. Some correct answers still take over three minutes or include excessive detail.

[The companion evidence report](https://github.com/tkarakai/lifeor2/blob/feat/life-query-contract/docs/evaluation/life-query-results-2026-09-18.md) records exact revisions, cohort results, fixture oracles, preserved failures and deployment limits. Completion and keyword checks are only smoke checks: answers were reviewed for scope, dates, meaning, coverage and unwanted writes, and write claims were checked against committed records. A finite suite is evidence for its cases, not proof that all possible natural-language questions are supported.
